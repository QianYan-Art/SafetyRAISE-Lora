# 终版总评测（交付配置）与解码研究的结果快照

日期：2026-10-08。评测对象：v3h2 合并后的 Q4_K_M（含重训 MTP 头）。所有案件为原创合成；评分与指标均为自动口径（确定性检查 + 脚本化审查者），**未经人工核实**；每个数字都是**单次采样**，开发 12 案，噪声大。本目录只放汇总，不放原始轨迹与案件文本。

## 评测设置

- 服务：`harness/orin/serve_delivery.sh`——compact 推理档位、思考预算 5120、KV 缓存 q8_0、6 槽位 × 每槽位 32768（评测当时；交付窗口之后放宽到 40960）、MTP 草稿上限 5（`SR_SPEC_BATCH_TOKENS=24`：6 路并发时每路 3 个）、草稿词表子集、**服务端默认采样 = 模型官方推荐**（temperature 1.0、top_k 20、top_p 0.95、min_p 0）。
- 流程：线上协议的完整流程（生成者 + 脚本化审查者 + 最多 2 轮修订），6 路并发，`--stable-limit 32768 --output-reserve 1 --max-tokens 32000`，检索 `sparse_half`；开发 12 案（编号 003 010 011 018 027 038 000 004 006 008 012 013）。入口 `harness/tools/final_eval.sh`。
- 对比的基线：v3f 全流程（预算 4000、f16 KV、llama-server 内置采样 0.8 / 40 / 0.95 / 0.05、库存构建、旧 MTP 头）与 v3h2 首回合快评（同样的内置采样，只跑首调用）。**预算、KV、采样、构建都与终版不同，只作参考。**

读法：

1. 首调用的确定性指标比 v3f 好很多、也比 v3h2 首回合快评干净（没有再出现 schema 额外键），但采样与预算都变了，只能说没有看到 v3h2 副作用复发，不能断言是改进。
2. 案件状态没有可分辨的变化：发布 6 对 7，两边各有几个案件翻转（000、008 由未发布变发布；003、012、038 由发布变未发布）。
3. **窗口截断是终版的主要问题**，见下节。

## 窗口截断（预算 5120 的代价）

34 次调用里 11 次以 `length` 结束，全部发生在提示已经很长的案件：首调用提示 23.8K（003），以及读完知识片段后提示 27.5 到 28.6K（010、027、038）。思考预算 5120 加答案放不下 32768：提示 28K 时只剩约 4.7K，思考与答案都出不来（输出只有 2 个 token）。基线预算 4000 时是 31 次里 2 次。003 在基线里首调用提示同样是 23.8K，预算 4000 能放下并发布，预算 5120 就被截断。逐调用明细见 `calls.md`。

可选对策：（a）系统层按精确 token 数控制：提示超过约 23K 就拆分，或给生成者请求设 `max_tokens`（窗口 − 提示 − 余量）并在提示长时降低思考预算；（b）把每槽位窗口放宽到 40960（6 槽位 q8_0 KV 约 8.5 GB；训练窗口只到 32768，更长窗口下的行为没有评过）；（c）预算退回 4000（只多出约 1.1K，解决不了读完片段后 28K 的提示）。

**决定（2026-10-08，评测之后）**：采用（b），交付窗口放宽到每槽位 40960。按本次评测的实际 token 数回算（思考封顶 5155，答案取观测最大 5194），34 次调用在 40960 下全部放得下，最紧的是 010 的第 4 次调用：提示 28645 + 5155 + 5194 = 38994，余 1966。放宽后只验证了 6 槽位能正常启动与生成（每槽位 `n_ctx` 40960，整机已用内存约 35 GB、可用约 27 GB），**没有重跑评测**。

## 思考预算的执行情况（评测之后核对）

服务端的思考预算是硬截断，**没有被超过**。逐调用核对了所有留存运行（思考 token = 响应中答案起点的位置，精确分词计数）：

| 运行 | 预算 | 有精确计数的调用 | 思考 token 最大 | 触顶的调用 | 触顶时的取值 |
| --- | --- | --- | --- | --- | --- |
| 终版总评测 | 5120 | 43（34 次生成者 + 9 次审查者） | 5155 | 19（都是生成者） | 5144–5155，最常见 5148（13 次） |
| 后训练采样（v3f，首调用） | 4000 | 108 | 4030 | 84 | 4018–4030，最常见 4024 |
| v3f 基线全流程 | 4000 | 44 | 4030 | 20 | 4026–4030 |
| v3h2 / v3h2 Q8_0 / v3h2 Q6_K / v3h 首回合 | 4000 | 12 / 12 / 7 / 6 | 4029 / 4028 / 4028 / 4028 | 10 / 7 / 6 / 5 | 4025–4029 |

触顶调用的取值比预算多出的 18 到 35 个 token，是服务端注入的“预算耗尽”提示语（`assets/templates/budget_msg.txt`，约 28 个 token）也算在思考里，不是模型多想的；上面结果表里的“思考中位 5144”同理。预算本身是实际约束：终版总评测 34 次生成者调用里 19 次触顶，写出完整报告（答案 ≥ 2000 token）的 19 次调用里 18 次触顶，没触顶的一次（011）思考 2380；真实的思考长度被截断，只知道下界。


## 速度（端到端）：没有比基线快，原因未查清

| | v3f 基线（预算 4000，f16 KV） | 终版 |
| --- | --- | --- |
| 墙钟 | 约 2.5 h | 约 3.0 h（04:50–07:50） |
| 生成者调用 / 提示 token / 生成 token | 31 / 61.2 万 / 19.0 万 | 34 / 73.4 万 / 20.8 万 |
| 案件耗时之和 / 最长案件 | 10.8 h / 1.34 h | 15.0 h / 2.07 h |
| 同口径中位解码速度（提示 16–22K，单路，含并发互相等待） | 4.96 tok/s | 4.56 tok/s |

终版的工作量更大（提示 token +20%、生成 token +9%、调用 +3 次，且 38% 的调用提示超过 22K，基线日志里没有这种调用），但单路微基准里的提升（词表子集 +17% 等）没有在端到端里体现为更快。可能的原因（**均未验证**）：q8_0 KV 在长上下文注意力上比 f16 慢；官方采样下思考段接受率更低；6 路并发时草稿预算 24（每路 3 个）在 16–25K 上下文里不是最优。一组长上下文的对照（f16 / q8_0 KV、库存 / 优化构建、草稿长度）已排好但**按要求中止，没有数据**。

服务端统计（`server_stats_final_v3h2m.json`，评测期间新增的日志）：34 次调用，提示 45.8 万 token（累计折算 161.6 token/s，含并发等待），生成 20.8 万 token，按 token 加权的单路解码 4.16 tok/s（中位 3.68），草稿接受率 0.610（141274/231589），平均接受长度中位 2.88；各位置接受率 0.769 / 0.616 / 0.518 / 0.167 / 0.150（第 4、5 位只在 ≤4 路并发时才画）。并发：6 路同时在生成占 44.1% 的时间、5 路 19.1%、4 路 13.2%，按时间平均 4.65 路在生成；有预填充在进行的时间占 21.2%。
