# SafetyRAISE-Lora 技术报告

版本：v0.2（2026-10-08，v3h2、MTP 头重训、解码优化与交付配置已补；终版总评测见 §6.10）

> 本文面向要**接着训练或复现**的人：把做了什么、为什么这样做、实测数字和踩过的坑写清楚。
> 所有案件均为原创合成；所有评分来自模型评审与确定性检查，**未经人工核实**；模型输出不是责任认定书。

## 摘要

SafetyRAISE 是一套把“事故材料 + 结构化事故信息（37 字段）+ 专家指导意见 + 知识库片段”组织成**交通事故分析报告**的系统。本项目的目标是让报告生成模型能**完全本地化**运行：在一台 Jetson AGX Orin 64 GB（统一内存，无独立显存）上，用 QLoRA 把 Qwen3.8-27B 训练成报告生成者，再合并量化为 Q4_K_M GGUF，配合重训的 MTP 草稿头由 llama.cpp 提供服务。

主要结论：

1. **路线**：保留学生模型自己的长思考，只让教师对“报告段”做最小改动修订（克制、引用规范），再训练（v3b–v3f）。剂量与案件多样性是关键：v3b 因剂量太小几乎等于基座，v3c 起第一次接近教师，之后在同一批案件上加样本收益趋零。
2. **当前最好的两个版本**是 v3d 与 v3f：在 50 个开发案上评审均分 19.58 / 19.82（满分 25），教师 21.24，未训练基座 16.18；硬门失败 4/50、8/50，教师 3/50。差距集中在“克制”和“引用相关性”。
3. **线上真实路径不是我们最初复刻的路径**：线上走 `report_harness`（生成者 + 独立审查者 + ≤2 轮修订的 JSON 协议）。因此后训练必须在“线上环境模拟器”里采样、过确定性门、再训练。我们据此做了模拟器、数据流水线与 v3h 后训练集。
4. **推理预算**：Qwen3.8 在该协议下 xhigh 档会把报告草稿写进思考、思考长到 3–4 万字符。我们增设了 `compact` 推理档位并在服务端设思考预算（采样与历次评测阶段为 4000 token，交付取 5120，§6.9）；4000 下 68/87 次采样调用触到预算，窗口按每槽位 32768 核算（交付窗口随后放宽到 40960，见 §6.10）。
5. **交付形态**：合并后的单个 GGUF（含重训的 MTP 头）。单路解码：思考区间约 16 token/s、答案区间约 31 token/s（草稿长度 5）；6 路并发合计约 27 到 31 token/s。运行时叠加 LoRA 更慢（解码约 −24%，MTP 接受率 72%→49%），故不做开关。
6. **后训练结果（v3h2）**：第一轮 v3h（26 行、13 次更新）因剂量太小几乎没改变行为；第二轮 v3h2（28 对偏好、选中回答的 NLL 权重 1.0、学习率 1e-4）在开发 12 案的首回合上，通过全部确定性检查的案件由 v3f 的 1/12 提到 4/12，37 项义务一致性的字段失败由 26 降到 6；代价是新出现 schema 额外键（2/12）与评价性字段缺归因（4 处）。详见 §6.8。
7. **交付配置**：Q4_K_M（与 Q8_0、Q6_K 对比无明显质量差）、KV 缓存 q8_0、思考预算 5120、每槽位 40960（总评测时为 32768）、MTP 草稿上限 5 且按在跑槽位数自适应、草稿词表子集、服务端默认采样用模型官方推荐值；见 §6.9、§7、§8。
8. **推理优化**（§8.2）：借鉴 ninfer 的“草稿词表子集”写成 llama.cpp 补丁，单路解码快 17%、输出逐位不变；MMVQ 放宽、预填充走 cuBLAS、n-gram 查表组合、置信度门限、概率式草稿采样都实测无收益；预填充约 238 token/s，已接近这台机器的持续算力上限。
9. **采样**（§8.3）：线上请求不带采样参数，llama-server 一直用的是内置默认（0.8 / top_k 40 / top_p 0.95 / min_p 0.05），而模型官方推荐 1.0 / 20 / 0.95 / 0。交付改为官方值；此前的评测都在内置默认下做的，与终版总评测的采样不同，对比只作参考。
10. **终版总评测的结论**（§6.10）：交付配置在开发 12 案的完整线上协议上发布 6、待审 5、失败 1（v3f 基线 7 / 4 / 1，差别不可分辨），首调用通过全部确定性检查 4/12（v3f 1/12）；**但 34 次调用里有 11 次被每槽位 32768 的窗口截断**（思考预算 5120 加答案放不下提示已超约 23K 的案件），端到端 3.0 h 没有比基线（2.5 h）快，原因未查清；与教师的差距和硬门失败率仍未达到既定通过线。仓库所有者随后把交付窗口放宽到每槽位 40960（按评测的实际 token 数回算，这 11 次都放得下；放宽后没有重跑评测，见 §6.10 和 [`handover.md`](handover.md) 第 6 节）。

## 1. 背景与目标

### 1.1 系统与任务

SafetyRAISE 的报告生成角色：输入是 37 个字段的事故信息 JSON（部分为空）、专家指导意见、首轮检索片段与一套长提示词；模型需判断资料是否足够，必要时调用只读工具补充证据，最终输出**候选报告**。线上由独立审查者复核，通不过不出报告。每次调用“输入 + 输出”约 2–3 万 token。

### 1.2 约束

- **全本地**：训练与推理都在 Orin 上，不租云 GPU。教师、评审可用外部 API（数据生成与打分，不是租算力）。
- **无人工评审条件**：验收靠确定性硬门、严格模型评审与统计检验；结论一律标“未经人工核实”。
- **合成数据可外发，真实案件永不外发**。
- **必须思考、但不能过度思考**；窗口按真实用量设计，不为“原生超长上下文”买单。

## 2. 硬件、系统与训练栈

| 项目 | 内容 |
| --- | --- |
| 设备 | Jetson AGX Orin 64GB Developer Kit（统一内存约 61 GiB 可用） |
| 系统 | JetPack 7.2.1（L4T R39.2.1）、Ubuntu 24.04、CUDA 13.2、MAXN 功耗模式 + `jetson_clocks` |
| 训练栈 | torch 2.14.1+cu130、transformers 5.18.0、peft 0.21.2、accelerate 1.15.0、bitsandbytes 0.50.2、fla-core 0.5.2、triton 3.8.0，另从源码编译 `causal-conv1d`（SM87） |
| 推理 | llama.cpp（CUDA，SM87；`--spec-type draft-mtp`）；GGUF Q4_K_M |

要点（详细踩坑见 [`reproduction.md`](reproduction.md)）：

- 官方 PyTorch 的 CUDA 13 aarch64 包无 SM87 预编译内核，靠 PTX 即时编译，首次运行慢；需设较大的 `CUDA_CACHE_MAXSIZE`。
- 线性注意力（Gated DeltaNet）的 fla Triton 内核可用；没装 `causal_conv1d` 时会退回 PyTorch 卷积，长序列训练步从 127 s 劣化到 441 s（4B 小模型实测），因此必须编译它。
- 实测算力：bf16 矩阵乘约 27–29 TFLOPS，内存带宽 191 GB/s（决定解码上限，27B Q4 约 12 token/s 理论上限）。

## 3. 基座与方法

### 3.1 基座

Qwen3.8-27B：稠密，64 层 = 48 层线性注意力（Gated DeltaNet）+ 16 层全注意力；hidden 5120、24 个 Q 头 / 4 个 KV 头、头维 256、词表 248,320；自带 1 层 MTP 头与 27 层视觉塔；BF16 约 55.6 GB。

训练底座用预量化 `unsloth/Qwen3.8-27B-bnb-4bit`（22.3 GB）：Orin 放不下 BF16 训练。该检查点有两个坑：非量化部分以 fp16 存储且 bnb 计算 dtype 为 fp16，需统一转 bf16 并把计算 dtype 改 bf16；跳过量化列表含 `in_proj_qkv` 等，这些层是普通线性层。

### 3.2 适配什么、冻结什么

- **LoRA**：r=16、α=32、dropout 0.05；作用于全注意力 `q/k/v/o_proj`、线性注意力 `in_proj_qkv / in_proj_z / out_proj`、MLP `gate/up/down_proj`。
- **只适配第 32–63 层**（`--lora_from 32`）：下半层前向包 `no_grad`，不存激活不反传。计算与激活内存约省 1/3，吞吐由 ~65 提到 ~95–112 token/s，24K 以上序列才放得下。代价：下半层不学习。
- 冻结：嵌入、lm_head、全部 RMSNorm、`in_proj_a/b`、`conv1d`、`A_log`、`dt_bias`（决定状态衰减与门控，适配有破坏长程记忆的风险）、MTP 头、视觉塔。
- 训练用纯文本类 `Qwen3_5ForCausalLM`，视觉塔在加载时丢弃；适配器 400 个张量中含 visual 的为 0。**因此 LoRA 不含视觉能力，视觉部分的微调是未来工作**（见扩展指南）。
- 可训练参数约 5440 万。

### 3.3 损失与实现要点

- 监督微调（SFT）：样本内对目标 token 取平均再对一次更新里的样本取平均；报告段与思考段可分别加权（v3c 起思考段 0.1、报告段 1.0，避免约 8K token 的自生成思考稀释报告信号）。
- 交叉熵按 1024 token 分块并用检查点，避免 24.8 万词表的 logits 撑爆内存；检查点连同优化器状态和数据游标保存，支持断点续训。
- 偏好优化（SimPO）：不需要参考模型，按长度归一化：`L = −log σ(β·(mean logp(chosen) − mean logp(rejected)) − γ)`；再加 chosen 的平均 NLL 项（`--sft_lambda`）。一次只在显存里放一条序列，用**梯度解耦**：先不求梯度算出两条序列的平均对数概率得到系数 `s=σ(−m)`，再对两条序列分别做带梯度的前后向，目标各为 `∓β·s·mean logp`。
- `--report_only`：只对最终回答段（`</think>` 之后）打分；两边**共享同一提示和同一思考前缀**，偏好信号只落在回答段。
- 锚点行（`kind` 以 `anchor` 开头、`rejected_ids` 为空）：只对 chosen 的回答段做 NLL，权重 `--anchor_lambda`。
- 独立复核：训练代码曾由 Codex（gpt-6.1-sol）与 Kimi（k3-256k）各自只读复核；SimPO 符号、梯度解耦系数、索引对齐、累积缩放、梯度裁剪顺序均无误（Codex 做 1000 组有限差分，最大误差约 2e-10）。

## 4. 数据

### 4.1 首版合成数据（v1，9 月）

100% 原创合成：1,698 条 SFT（534 个事故组）、534 条 RL 任务与奖励参考、开发/测试各 50 组；约 294 万 token，序列仅 671–4,568 token。其缺口是**形态**不对：没有真实的检索往返、没有万 token 量级的长提示，输入反而比真实更长（真实案例仅约 24 个字段非空、合计约 210 字）。详见 `datasets/v1-synthetic-release/DATA-CARD.md`。

### 4.2 评测台与合成案件

`harness/sr_eval/` 复刻生产提示拼接并冻结其渲染逻辑，核心思想“同一提示、同一检索器、同一硬门”。案件由强模型按 37 字段模板生成，事实量分稀疏/中等/丰富三档（稀疏档约 24 个字段、150 字，贴近真实），再按生产的指导意见提示词生成指导意见：**train 240 / dev 50 / test 50**，全部标记为合成。

硬门（确定性）：无报告、输出截断、工具标记泄入、未知工具、引用不在可见片段、法条或国标号不在可见文本、速度与钟点编造、定罪量刑措辞、证件/手机/邮箱泄漏。评审为五维量表（事实完整性、证据边界、因果与责任、法规引用、文书可用性，各 1–5）加简洁性，要求先列缺陷并引用报告原文。

### 4.3 教师与评审

教师/评审早期用 `gpt-6-luna`（OpenRouter），MiniMax 作补充；严格评审排名与 Codex、Kimi 盲评方向一致。后训练阶段决定**不再使用 OpenRouter**：教师/修订者用 MiniMax-M3.1-Flash-Preview（max 档），盲评用 Codex（gpt-6.1-sol xhigh）、Kimi（k3-256k）与 DeepSeek（flash，high）。luna 不再参与打分。

## 6. 线上真实路径与后训练

### 6.1 发现

读线上部署后确认：线上生成走新 `report_harness`（demo 模式）：**生成者 + 独立审查者 + 最多 2 轮修订，JSON 协议**，审查不过不出报告（`needs_review`）。此前评测台复刻的是旧路径（原生 tool call + 直接 Markdown），与线上不一致。协议级说明见 [`live-protocol.md`](live-protocol.md)。结论：**v3 谱系的数据保留为“写作能力”基础，但后训练必须在线上环境里采样、过门、训练。**

### 6.2 线上环境模拟器

`harness/sr_eval/live/`：用线上同款提示/协议模块（需另行取回，见复现文档）复刻一次运行：首检由程序执行（top_k=3）、生成者 JSON 协议（`json_object`）、四个只读工具、独立审查者、≤2 轮修订、窗口门。检索用无嵌入的确定性稀疏近似（`sparse_half` 与 `fallback` 两种模式，采样用 `sparse_half`）。

### 6.3 推理档位 `compact` 与思考预算

Qwen3.8 聊天模板只接受 `xhigh / medium / low`（传 `high` 会 HTTP 500）。在线上协议下：

- `xhigh`：正文句子约 100% 先在思考里起草再原样抄进 JSON，总思考中位约 3.7 万字符（旧格式 v3f 仅 8,660）。
- `medium`：思考短，但常给出空/残缺候选或先发工具回合。

做法：新增自定义档位 `compact`（模板见 `assets/templates/qwen3.8-compact.chat_template.jinja`），指令为“简要核对关键事实与字段状态、决定结构与引用来源、每个疑点只想一次；不要在思考里写出最终答案或 JSON；计划清楚就停止思考直接写答案”。服务端再加硬预算：`--reasoning-budget 4000`，耗尽时注入“Thinking budget reached… 直接写最终 JSON”的提示语。

实测：87 次采样调用中 68 次（78%）触到 4000 预算，思考 token 中位 4,024；答案（最终 JSON）token 中位 2.9K、p90 4.0K、最大 5.0K。后训练 `--report_only` 只训练回答段，**思考长度主要靠 compact 指令 + 服务端预算控制，而非训练**。

### 6.4 窗口 32768 的截断核算

线上请求**不带 `max_tokens`**（容量只用于预留，不转成请求截断参数），所以截断线就是 llama-server 每槽位上下文：`提示 + 思考 + 答案 ≤ 32768`，超出即 `finish_reason=length`，JSON 被截断（协议失败）；提示本身超限则服务端直接报错。

| 答案假设 | 首个提示须 ≤ | 116 案中放得下 |

| 中位 2.9K | 25.8K | 114（98%） |
| p90 4.0K | 24.7K | 112（97%） |

（思考按 4040 计。首提示 token：最小 14.5K、中位 16.8K、最大 30.8K。）读一次片段后下一回合提示 +6.3～6.5K；修订轮再 +3.5～5K，**工具回合与修订轮是主要溢出点**，需系统层“超限拆成多次调用”。v3f 在开发 12 案（部署口径）上的基线：7 发布、3 协议无效、1 证据未找到、1 窗口溢出（读片段后第 2 回合提示 28.4K，答案被 `length` 截断）。预算改为 5120 后截断线下移约 1.1K，实测见 §6.10 和 [`deployment.md`](deployment.md) §4；交付窗口后来放宽到 40960，见 §6.10。

### 6.5 后训练数据流水线（v3h）

1. **采样**：学生（v3f，compact + 预算 4000，`sparse_half` 检索）在 110 个训练案的**第 1 回合**采样（窗口门：提示 ≤25,168，让答案还有空间）；108 个得到有效首调用。
2. **确定性评估**：契约、来源访问（必须先读后引）、37 项义务、`quote` 唯一、规则摘录不得作依据，以及“解读指标”（关键事实覆盖、空字段不编造、评价字段归因、义务与字段状态一致、证据引用指向正确字段）。指标分 pass / fail / unknown，unknown 单列。
3. **修订**：不合格的由 MiniMax（max 档）按清单做**最小改动**修订（保留学生结构与措辞、不新增材料外事实），最多 2 次，仍不过则丢弃。111 条记录中 86 条通过（67 教师修订 + 19 学生原样合格），25 条丢弃（22 耗尽、3 上下文无效）。
4. **构造训练行**：`pair_revised`（学生失败 vs 修订通过，同提示同思考前缀，只在回答段不同）、锚点 `anchor_final/anchor_tool`（修订版回答，只做 NLL）；另有 12 类单错种子对（`seeded.py`）备用。窗口门：提示 + max(回答) ≤ 32768。
5. **审查**：见下节。

指标曾两次收紧，都源自盲评发现的**系统性错误**：(a) 非空字段被写成“未提供”（如“交通方式=机动车通行”却写“该字段未提供”）；(b) 事故认定原因/初查原因/主要违法行为/事故责任为空时不得标 `not_relevant`（必须 `uncertain`）。此外修了一次校验误判：缺失标记词表漏了“为空”，使约 46% 的修订被误判为“耗尽”。

## 7. 合并、量化与部署

1. **合并**：流式读取官方 BF16（18 个分片），对被适配的权重做 `W' = W + (α/r)·B·A`（fp32 计算、转回 bf16），未适配张量原样复制，约 12 分钟；可用 `--mtp_overlay` 覆盖 `mtp.*`。
2. **转 GGUF**：`convert_hf_to_gguf.py` 输出 bf16（54.6 GB），转换器会导出 MTP 层（`qwen35.nextn_predict_layers = 1`）；用 Q8_0 中转可把磁盘峰值从约 104 GB 降到约 80 GB。
3. **量化**：`llama-quantize` Q4_K_M → 16.8 GB（朴素量化，无 imatrix）。
4. **服务**：`harness/orin/serve_llama.sh`：`--reasoning-effort compact`、`--reasoning-budget` + 提示语、每槽位上下文（缺省 32768）、`--spec-type draft-mtp --spec-draft-n-max 5`；交付入口 `serve_delivery.sh` 在此之上加优化构建、草稿词表子集、按负载自适应草稿长度、官方采样、KV q8_0 与每槽位 40960 的窗口（见 §6.10、§8.2、§8.3）。

速度实测（Orin MAXN，v2a 时代、同一份 10,550 token 的真实提示，思考开头段）：预填充约 230 token/s；解码无投机 7.49 token/s；官方 MTP 权重（草稿 3）13.74 token/s；当时重训的 MTP 头（草稿 5）16.30 token/s（接受率 45.7%，草稿 3 为 57.6%）。**v3h2 终版的速度见 §8.2**（分思考 / 答案区间与并发路数）。

关于“能不能开关 LoRA”：llama.cpp 支持把 LoRA 转 GGUF 并在运行时叠加/调缩放，但实测（基座 IQ3_S + MTP）解码 14.7 → 11.2 token/s、接受率 72% → 49%、预填充 −10%，且 LoRA 无法合并进量化权重，故**交付合并版单个 GGUF**。

**量化选择与交付配置（2026-10-07）**：v3h2 合并后分别做 Q4_K_M、Q8_0，并在开发 12 案首回合上同口径对比（Q6_K 由 Q8_0 重量化，评测只跑了 7 案就按仓库所有者指示停止）；各量化均为单次采样的自动指标：

## 8. MTP 头自蒸馏与推理优化

### 8.1 MTP 头自蒸馏

MTP 头是在原始基座上训练的，主模型被微调后接受率从 72% 掉到约 48%（v3f 上约 42%）。结构按 llama.cpp 与 vLLM 的实现核对：输入为主模型最后一层归一化后的隐藏状态 h 与下一个 token 嵌入，各过 RMSNorm、拼接后经 `fc`（10240→5120）、一个全注意力解码层、`mtp.norm` 与共享 lm_head；权重为官方 BF16 里 15 个 `mtp.` 张量（约 4.25 亿参数）。训练：冻结主模型（含 LoRA），缓存隐藏状态后在缓存上训 `mtp.*`；损失为主模型分布对 MTP 分布的 KL + 0.2×交叉熵，展开 3 步（权重 1.0/0.6/0.4，后两步用 MTP 自己的输出当隐藏状态，对应 llama.cpp 的链式草稿）。MTP 只影响速度，不影响贪心输出。

**终版 v3h2 的重训**（2026-10-07 21:17 启动，2026-10-08 01:50 训完）：训练序列为 60 条学生在线上协议下的输出（约 140 万 token），留出集是 v3h2 开发案首回合的 10 条输出（21.4 万个监督 token），3 轮、45 次更新（梯度累积 4）、学习率 5e-5 余弦衰减。离线一致率（MTP 头预测与主模型下一步预测相同的比例，教师强制）：

| | 留出集损失 | 第 1 步 | 第 2 步 | 第 3 步 | 三步平均 |
| --- | --- | --- | --- | --- | --- |
| 官方头（未训练） | 1.5602 | 0.9013 | 0.8254 | 0.7656 | 0.8308 |
| 第 1 轮 | 1.1180 | 0.9001 | 0.8396 | 0.7961 | 0.8453 |
| 第 2 轮 | 1.0453 | 0.9006 | 0.8460 | 0.8068 | 0.8511 |
| **第 3 轮（采用）** | **0.9492** | **0.9071** | **0.8567** | **0.8194** | **0.8611** |

第 1 步基本不变（官方头在微调后的主模型上本来就很准），提升集中在链式的第 2、3 步（+3.1、+5.4 个百分点）。训练集一致率 0.9125/0.8622/0.8197，与留出集接近，没有明显过拟合。离线数字是教师强制的，真实接受率（量化后、带采样）低得多，实测见 8.2。

**工程教训**：第一次训练在第 2 轮因显存不足中断（每块 logits 及其 log_softmax 保留到整步反传，监督区间长时峰值 50 GiB，Orin 统一内存里系统自占约 9 GiB）。修复：逐块反传（每块损失立刻对该块输入反传并丢弃 logits，块梯度拼好后一次性反传过 MTP 层，数学上等价）、每轮刷新最佳即落盘、启用 `expandable_segments`；峰值降到 28.7 GiB，第 5 步指标与旧跑一致。

### 8.2 解码与预填充优化（借鉴 ninfer）

详细表格、脚本与复现方法在 `inference/README.md`，这里只记结论。**测法**：一次调用的两段差别很大——思考约 4 到 5K token、占约四分之三的时间，草稿接受率四成上下；答案是结构化 JSON，接受率约 95%——所以分区间测（思考区间 / 答案区间 / N 路并发 / 批大小曲线），全部在交付配置下。交付形态下 62% 的时间 6 路同时在生成，有预填充在进行的时间约占 33%（早先全流程服务日志的统计；终版总评测期间实测为 44% 和 21%，见 §6.10）。

- **机器上限**：可持续读带宽最高 162.6 GB/s（不是 190）；单 token 前向 137 ms，对应带宽下限 104 ms；8 个 token 以内的验证批几乎不比单 token 贵，之后每多一个 token 约贵 3 到 7 ms，6 路并发时验证批（路数 ×（1+草稿长度））已是算力受限。预填充约 238 token/s，nsys 看 MMQ 占 71.9%、GPU 空档只有 0.6%，已接近持续算力上限。
- **采用：草稿词表子集（补丁 0001，借鉴 ninfer 的 proposal head）**：草稿每步要读 MTP 块加整个输出头，输出头占 80% 的字节；只用按词频排序的 32768 行来猜，验证仍用完整输出头。单路思考区间 13.48 → 15.81 token/s、答案区间 26.11 → 30.52 token/s，**都快 17%**，两种构建的生成文本、草稿数、接受数逐位相同；6 路并发合计 25.0 → 27.5 token/s。
- **采用：按负载自适应草稿长度（补丁 0003）**：6 路并发时验证批 =“路数 ×（1+草稿长度）”，被拒的草稿白占算力。`SR_SPEC_BATCH_TOKENS=24`：6 路时每路 3 个草稿（实测 6 路思考段最优，31.2 对草稿 5 的 27.5 token/s），≤4 路时 5 个。
- **没采用（均有实测）**：放宽 MMVQ 到 8 列（更慢，6 列 209 对 150 ms）；预填充走反量化 + cuBLAS（bf16 最好只比 MMQ 快 3.7%，与 MMQ 的 KL 散度均值 0.20，数值差异比预期大）；n-gram 查表在前、MTP 兜底（答案段反而更慢，23.4 对 29.9 token/s）；置信度门限 0.5 / 0.7（6 路并发合计腰斩）；概率式草稿采样（官方采样下思考 +2.4%、答案 −7%）；单路草稿长度 8（答案区间 +19%、思考区间 −12%，加权后 5 更好）。
- **没做**：线性注意力状态快照的 ReplaySSM（验证时每个位置存一份 144 MiB 的完整状态，6 路 × 草稿 5 时每次约 5 GB 写入，估计 10% 到 15%，改动牵涉循环记忆管理，风险高）；MMQ 小批量（17 到 24 个 token 这一档比 16 个异常贵 59 ms）的瓦片参数调优；6 路并发的 nsys 剖析。
- **训练特征与服务特征没有失配**：用 llama.cpp 导出服务模型（Q4_K_M）的末层隐藏状态，再用 HF 里的头算教师强制一致率，新头 0.926 / 0.878 / 0.844，官方头 0.922 / 0.853 / 0.798，不低于训练时用 NF4 + LoRA 特征得到的数字。思考区间接受率低主要是采样温度和文本难预测。

### 8.3 采样

线上请求不带 `temperature`、`top_p`（`check_conformance.py` 已核对），所以服务端的默认采样决定模型的采样行为。llama-server 的内置默认是 temperature 0.8、top_k 40、top_p 0.95、min_p 0.05，我们的历次评测和 v3h / v3h2 的线上协议数据都在这个默认下产生；而模型自带的 `generation_config.json` 推荐 temperature 1.0、top_k 20、top_p 0.95。训练（SFT / 偏好 / MTP）是对给定文本的教师强制，没有采样温度这个概念；温度 0 只用于测速探针、MTP 一致率（取 argmax）和评审打分。**交付改为官方采样**（服务端默认值，请求带了采样参数则以请求为准）。官方采样下速度没有变差（思考区间 16.45 token/s，接受率 40%）。因此终版总评测（§6.10）与旧基线的采样不同，对比只作参考。

## 9. 局限与风险

- 数据全为合成；评分全为自动口径，未经人工核实；独立评审之间存在显著分歧与噪声（Codex 严、DeepSeek 松）。
- 与教师的差距（−1.4～−1.7 分）与硬门失败率（v3f 8/50 对教师 3/50）尚未达到既定通过线；v3h2 的首回合改善见 §6.8，终版总评测见 §6.10。
- 后训练集规模很小（v3h 26 行、v3h2 28 对偏好），主要用于“线上协议适配 + 37 项解读”的校正，不是能力的大幅提升。
- 窗口：终版总评测按每槽位 32768 跑，实测 11/34 的调用被截断（§6.10）；交付窗口已放宽到 40960（2026-10-08），但放宽后没有重跑评测，训练窗口仍只到 32768，更长窗口下的行为没有评过；工具回合与修订轮在提示超过约 30.6K 时仍会超限，需系统层拆多次调用。
- 线上请求若带 `reasoning.effort=high`，Qwen3.8 模板会报错，服务端必须固定档位；线上 `report_harness` 的端点校验仅认固定域名，接入本地模型需系统层改动；`json_object` 与思考段的交互需用终版模型实测。
- v3h2 的副作用：schema 额外键（2/12）、评价性字段缺归因（4 处）；量化与预算的对比均为 12 案单次采样，噪声大；交付配置（预算 5120、KV q8_0、官方采样）只在终版总评测（§6.10）里整体评过一次，没有拆开单独评测每一项。
- 采样：历次评测与 v3h / v3h2 训练数据都在 llama-server 内置默认采样（0.8 / 40 / 0.95 / 0.05）下产生，交付改成了模型官方推荐（1.0 / 20 / 0.95 / 0）；终版总评测用官方采样，与旧基线不可严格对比。
- 速度：并发数字用约 5K token 的提示测，真实调用上下文 16 到 25K，并发时长上下文的注意力与线性注意力状态快照开销没有用 nsys 拆开；区间探针是单样本，草稿长度 3 与 5 的差别在噪声内。
- 模型不得用于正式定责；输出需人工复核。

## 10. 路线图

1. （已完成）v3h2 的 MTP 重训、解码速度优化、按交付配置做终版总评测并交付；结果见 §6.10、§8。
2. **验证 40960 窗口**（最优先）：交付窗口已放宽到每槽位 40960。重跑开发 12 案总评测（`WIN=40960 bash harness/tools/final_eval.sh`），确认窗口截断消失，再看长上下文下的速度与质量有没有变化；提示超过约 30.6K 的长尾仍要系统层按精确 token 数拆分或设 `max_tokens`（[`deployment.md`](deployment.md) §4）；思考预算有空间放开测一次真实分布（[`handover.md`](handover.md) 第 6 节）；必要时按新窗口补更长上下文的数据（第 7 项）。
3. 查清端到端没有变快的原因：长上下文（提示约 16K）下 6 路并发的对照——KV f16 / q8_0 × 库存 / 优化构建 × 草稿长度（配置模板 `harness/orin/multi_configs.txt`）；再决定交付配置里 KV 精度和验证批预算是否要改。
4. 放开思考预算测一次真实的思考长度分布（4000 预算下 58–83% 的首调用触顶，真实长度被截断、只知下界），再结合窗口方案重新定预算。
5. 解码继续优化的方向（按预期收益排序）：线性注意力状态快照的 ReplaySSM（估计 10% 到 15%）；MMQ 小批量（17 到 24 个 token 一档异常贵）的瓦片参数调优；6 路并发的 nsys 剖析（找长上下文下注意力与状态快照的开销）；思考区间接受率（占时间四分之三）仍是最大杠杆。
6. 与教师的差距和硬门失败率：更多“线上环境里的真实失败对”（路线 A，见 [`handover.md`](handover.md)），修复数据中的“过度保守”和“复合断言引用不全”，扩大偏好对规模；评审口径引入人工抽样。
7. 更长上下文数据（超过 28,000 的提示、多回合工具往返、修订轮），配合系统层“超限拆分”，并按拆分后的输入形态补数据。
8. 视觉部分微调（让模型更好地从图片/关键帧产出 37 字段事故信息），并研究与报告 LoRA 的融合；融合需用 BF16 基座合并后重新量化与重训 MTP。
