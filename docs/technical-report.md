# SafetyRAISE-Lora 技术报告

版本：v0.1（2026-10-07，后训练 v3h 训练中，相关结果以“待补”标注，完成后更新）

> 本文面向要**接着训练或复现**的人：把做了什么、为什么这样做、实测数字和踩过的坑写清楚。
> 所有案件均为原创合成；所有评分来自模型评审与确定性检查，**未经人工核实**；模型输出不是责任认定书。

## 摘要

SafetyRAISE 是一套把“事故材料 + 结构化事故信息（37 字段）+ 专家指导意见 + 知识库片段”组织成**交通事故分析报告**的系统。本项目的目标是让报告生成模型能**完全本地化**运行：在一台 Jetson AGX Orin 64 GB（统一内存，无独立显存）上，用 QLoRA 把 Qwen3.8-27B 训练成报告生成者，再合并量化为 Q4_K_M GGUF，配合重训的 MTP 草稿头由 llama.cpp 提供服务。

主要结论：

1. **路线**：保留学生模型自己的长思考，只让教师对“报告段”做最小改动修订（克制、引用规范），再训练（v3b–v3f）。剂量与案件多样性是关键：v3b 因剂量太小几乎等于基座，v3c 起第一次接近教师，之后在同一批案件上加样本收益趋零。
2. **当前最好的两个版本**是 v3d 与 v3f：在 50 个开发案上评审均分 19.58 / 19.82（满分 25），教师 21.24，未训练基座 16.18；硬门失败 4/50、8/50，教师 3/50。差距集中在“克制”和“引用相关性”。
3. **线上真实路径不是我们最初复刻的路径**：线上走 `report_harness`（生成者 + 独立审查者 + ≤2 轮修订的 JSON 协议）。因此后训练必须在“线上环境模拟器”里采样、过确定性门、再训练。我们据此做了模拟器、数据流水线与 v3h 后训练集。
4. **推理预算**：Qwen3.8 在该协议下 xhigh 档会把报告草稿写进思考、思考长到 3–4 万字符。我们增设了 `compact` 推理档位并在服务端设 4000 token 的思考预算；68/87 次采样调用触到预算，窗口按每槽位 32768 核算。
5. **交付形态**：合并后的单个 GGUF（解码约 16 token/s，MTP 草稿长度 5）。运行时叠加 LoRA 更慢（解码约 −24%，MTP 接受率 72%→49%），故不做开关。

## 1. 背景与目标

### 1.1 系统与任务

SafetyRAISE 的报告生成角色：输入是 37 个字段的事故信息 JSON（部分为空）、专家指导意见、首轮检索片段与一套长提示词；模型需判断资料是否足够，必要时调用只读工具补充证据，最终输出**候选报告**。线上由独立审查者复核，通不过不出报告。每次调用“输入 + 输出”约 2–3 万 token。

### 1.2 约束

- **全本地**：训练与推理都在 Orin 上，不租云 GPU。教师、评审可用外部 API（数据生成与打分，不是租算力）。
- **无人工评审条件**：验收靠确定性硬门、严格模型评审与统计检验；结论一律标“未经人工核实”。
- **合成数据可外发，真实案件永不外发**。
- **必须思考、但不能过度思考**；窗口按真实用量设计，不为“原生超长上下文”买单。

## 2. 硬件、系统与训练栈

| 项目 | 内容 |
| --- | --- |
| 设备 | Jetson AGX Orin 64GB Developer Kit（统一内存约 61 GiB 可用） |
| 系统 | JetPack 7.2.1（L4T R39.2.1）、Ubuntu 24.04、CUDA 13.2、MAXN 功耗模式 + `jetson_clocks` |
| 训练栈 | torch 2.14.1+cu130、transformers 5.18.0、peft 0.21.2、accelerate 1.15.0、bitsandbytes 0.50.2、fla-core 0.5.2、triton 3.8.0，另从源码编译 `causal-conv1d`（SM87） |
| 推理 | llama.cpp（CUDA，SM87；`--spec-type draft-mtp`）；GGUF Q4_K_M |

要点（详细踩坑见 [`reproduction.md`](reproduction.md)）：

- 官方 PyTorch 的 CUDA 13 aarch64 包无 SM87 预编译内核，靠 PTX 即时编译，首次运行慢；需设较大的 `CUDA_CACHE_MAXSIZE`。
- 线性注意力（Gated DeltaNet）的 fla Triton 内核可用；没装 `causal_conv1d` 时会退回 PyTorch 卷积，长序列训练步从 127 s 劣化到 441 s（4B 小模型实测），因此必须编译它。
- 实测算力：bf16 矩阵乘约 27–29 TFLOPS，内存带宽 191 GB/s（决定解码上限，27B Q4 约 12 token/s 理论上限）。

## 3. 基座与方法

### 3.1 基座

Qwen3.8-27B：稠密，64 层 = 48 层线性注意力（Gated DeltaNet）+ 16 层全注意力；hidden 5120、24 个 Q 头 / 4 个 KV 头、头维 256、词表 248,320；自带 1 层 MTP 头与 27 层视觉塔；BF16 约 55.6 GB。

训练底座用预量化 `unsloth/Qwen3.8-27B-bnb-4bit`（22.3 GB）：Orin 放不下 BF16 训练。该检查点有两个坑：非量化部分以 fp16 存储且 bnb 计算 dtype 为 fp16，需统一转 bf16 并把计算 dtype 改 bf16；跳过量化列表含 `in_proj_qkv` 等，这些层是普通线性层。

### 3.2 适配什么、冻结什么

- **LoRA**：r=16、α=32、dropout 0.05；作用于全注意力 `q/k/v/o_proj`、线性注意力 `in_proj_qkv / in_proj_z / out_proj`、MLP `gate/up/down_proj`。
- **只适配第 32–63 层**（`--lora_from 32`）：下半层前向包 `no_grad`，不存激活不反传。计算与激活内存约省 1/3，吞吐由 ~65 提到 ~95–112 token/s，24K 以上序列才放得下。代价：下半层不学习。
- 冻结：嵌入、lm_head、全部 RMSNorm、`in_proj_a/b`、`conv1d`、`A_log`、`dt_bias`（决定状态衰减与门控，适配有破坏长程记忆的风险）、MTP 头、视觉塔。
- 训练用纯文本类 `Qwen3_5ForCausalLM`，视觉塔在加载时丢弃；适配器 400 个张量中含 visual 的为 0。**因此 LoRA 不含视觉能力，视觉部分的微调是未来工作**（见扩展指南）。
- 可训练参数约 5440 万。

### 3.3 损失与实现要点

- 监督微调（SFT）：样本内对目标 token 取平均再对一次更新里的样本取平均；报告段与思考段可分别加权（v3c 起思考段 0.1、报告段 1.0，避免约 8K token 的自生成思考稀释报告信号）。
- 交叉熵按 1024 token 分块并用检查点，避免 24.8 万词表的 logits 撑爆内存；检查点连同优化器状态和数据游标保存，支持断点续训。
- 偏好优化（SimPO）：不需要参考模型，按长度归一化：`L = −log σ(β·(mean logp(chosen) − mean logp(rejected)) − γ)`；再加 chosen 的平均 NLL 项（`--sft_lambda`）。一次只在显存里放一条序列，用**梯度解耦**：先不求梯度算出两条序列的平均对数概率得到系数 `s=σ(−m)`，再对两条序列分别做带梯度的前后向，目标各为 `∓β·s·mean logp`。
- `--report_only`：只对最终回答段（`</think>` 之后）打分；两边**共享同一提示和同一思考前缀**，偏好信号只落在回答段。
- 锚点行（`kind` 以 `anchor` 开头、`rejected_ids` 为空）：只对 chosen 的回答段做 NLL，权重 `--anchor_lambda`。
- 独立复核：训练代码曾由 Codex（gpt-6.1-sol）与 Kimi（k3-256k）各自只读复核；SimPO 符号、梯度解耦系数、索引对齐、累积缩放、梯度裁剪顺序均无误（Codex 做 1000 组有限差分，最大误差约 2e-10）。

## 4. 数据

### 4.1 首版合成数据（v1，9 月）

100% 原创合成：1,698 条 SFT（534 个事故组）、534 条 RL 任务与奖励参考、开发/测试各 50 组；约 294 万 token，序列仅 671–4,568 token。其缺口是**形态**不对：没有真实的检索往返、没有万 token 量级的长提示，输入反而比真实更长（真实案例仅约 24 个字段非空、合计约 210 字）。详见 `datasets/v1-synthetic-release/DATA-CARD.md`。

### 4.2 评测台与合成案件

`harness/sr_eval/` 复刻生产提示拼接并冻结其渲染逻辑，核心思想“同一提示、同一检索器、同一硬门”。案件由强模型按 37 字段模板生成，事实量分稀疏/中等/丰富三档（稀疏档约 24 个字段、150 字，贴近真实），再按生产的指导意见提示词生成指导意见：**train 240 / dev 50 / test 50**，全部标记为合成。

硬门（确定性）：无报告、输出截断、工具标记泄入、未知工具、引用不在可见片段、法条或国标号不在可见文本、速度与钟点编造、定罪量刑措辞、证件/手机/邮箱泄漏。评审为五维量表（事实完整性、证据边界、因果与责任、法规引用、文书可用性，各 1–5）加简洁性，要求先列缺陷并引用报告原文。

### 4.3 教师与评审

教师/评审早期用 `gpt-6-luna`（OpenRouter），MiniMax 作补充；严格评审排名与 Codex、Kimi 盲评方向一致。后训练阶段决定**不再使用 OpenRouter**：教师/修订者用 MiniMax-M3.1-Flash-Preview（max 档），盲评用 Codex（gpt-6.1-sol xhigh）、Kimi（k3-256k）与 DeepSeek（flash，high）。luna 不再参与打分。

1. 自检类训练内容必须与证据绑定（摘录可见片段原文），否则训出“伪核对”（v3e）。

## 6. 线上真实路径与后训练

### 6.1 发现

读线上部署后确认：线上生成走新 `report_harness`（demo 模式）：**生成者 + 独立审查者 + 最多 2 轮修订，JSON 协议**，审查不过不出报告（`needs_review`）。此前评测台复刻的是旧路径（原生 tool call + 直接 Markdown），与线上不一致。协议级说明见 [`live-protocol.md`](live-protocol.md)。结论：**v3 谱系的数据保留为“写作能力”基础，但后训练必须在线上环境里采样、过门、训练。**

### 6.2 线上环境模拟器

`harness/sr_eval/live/`：用线上同款提示/协议模块（需另行取回，见复现文档）复刻一次运行：首检由程序执行（top_k=3）、生成者 JSON 协议（`json_object`）、四个只读工具、独立审查者、≤2 轮修订、窗口门。检索用无嵌入的确定性稀疏近似（`sparse_half` 与 `fallback` 两种模式，采样用 `sparse_half`）。

### 6.3 推理档位 `compact` 与思考预算

Qwen3.8 聊天模板只接受 `xhigh / medium / low`（传 `high` 会 HTTP 500）。在线上协议下：

- `xhigh`：正文句子约 100% 先在思考里起草再原样抄进 JSON，总思考中位约 3.7 万字符（旧格式 v3f 仅 8,660）。
- `medium`：思考短，但常给出空/残缺候选或先发工具回合。

做法：新增自定义档位 `compact`（模板见 `assets/templates/qwen3.8-compact.chat_template.jinja`），指令为“简要核对关键事实与字段状态、决定结构与引用来源、每个疑点只想一次；不要在思考里写出最终答案或 JSON；计划清楚就停止思考直接写答案”。服务端再加硬预算：`--reasoning-budget 4000`，耗尽时注入“Thinking budget reached… 直接写最终 JSON”的提示语。

实测：87 次采样调用中 68 次（78%）触到 4000 预算，思考 token 中位 4,024；答案（最终 JSON）token 中位 2.9K、p90 4.0K、最大 5.0K。后训练 `--report_only` 只训练回答段，**思考长度主要靠 compact 指令 + 服务端预算控制，而非训练**。

### 6.4 窗口 32768 的截断核算

线上请求**不带 `max_tokens`**（容量只用于预留，不转成请求截断参数），所以截断线就是 llama-server 每槽位上下文：`提示 + 思考 + 答案 ≤ 32768`，超出即 `finish_reason=length`，JSON 被截断（协议失败）；提示本身超限则服务端直接报错。

| 答案假设 | 首个提示须 ≤ | 116 案中放得下 |
| --- | --- | --- |
| 中位 2.9K | 25.8K | 114（98%） |
| p90 4.0K | 24.7K | 112（97%） |
| 观测最大 5.0K | 23.7K | 107（92%） |

（思考按 4040 计。首提示 token：最小 14.5K、中位 16.8K、最大 30.8K。）读一次片段后下一回合提示 +6.3～6.5K；修订轮再 +3.5～5K，**工具回合与修订轮是主要溢出点**，需系统层“超限拆成多次调用”。v3f 在开发 12 案（部署口径）上的基线：7 发布、3 协议无效、1 证据未找到、1 窗口溢出（读片段后第 2 回合提示 28.4K，答案被 `length` 截断）。详见 [`deployment.md`](deployment.md)。

### 6.5 后训练数据流水线（v3h）

1. **采样**：学生（v3f，compact + 预算 4000，`sparse_half` 检索）在 110 个训练案的**第 1 回合**采样（窗口门：提示 ≤25,168，让答案还有空间）；108 个得到有效首调用。
2. **确定性评估**：契约、来源访问（必须先读后引）、37 项义务、`quote` 唯一、规则摘录不得作依据，以及“解读指标”（关键事实覆盖、空字段不编造、评价字段归因、义务与字段状态一致、证据引用指向正确字段）。指标分 pass / fail / unknown，unknown 单列。
3. **修订**：不合格的由 MiniMax（max 档）按清单做**最小改动**修订（保留学生结构与措辞、不新增材料外事实），最多 2 次，仍不过则丢弃。111 条记录中 86 条通过（67 教师修订 + 19 学生原样合格），25 条丢弃（22 耗尽、3 上下文无效）。
4. **构造训练行**：`pair_revised`（学生失败 vs 修订通过，同提示同思考前缀，只在回答段不同）、锚点 `anchor_final/anchor_tool`（修订版回答，只做 NLL）；另有 12 类单错种子对（`seeded.py`）备用。窗口门：提示 + max(回答) ≤ 32768。
5. **审查**：见下节。

指标曾两次收紧，都源自盲评发现的**系统性错误**：(a) 非空字段被写成“未提供”（如“交通方式=机动车通行”却写“该字段未提供”）；(b) 事故认定原因/初查原因/主要违法行为/事故责任为空时不得标 `not_relevant`（必须 `uncertain`）。此外修了一次校验误判：缺失标记词表漏了“为空”，使约 46% 的修订被误判为“耗尽”。

### 6.6 独立审查与口径（如实记录）

| 轮次 | 评审 | 结果 |
| --- | --- | --- |
| 1 | Codex，15 份 | 严格口径 9/15 过；暴露上述两类系统性错误 → 加确定性检查并重做修订 |
| 2 | Codex + DeepSeek，15 份 | Codex 10/15 不合格（多为过度保守、复合断言引用不全），DeepSeek 仅 1/15（宽松）；**偏好方向 13/13 一致认可** |
| 锚点全量 | Codex，86 条锚点 | 40 条通过，46 条不通过 |
| 最终抽检 | Codex + DeepSeek，15 份 | 偏好方向 8/8 一致认可；7 条锚点 3 条双过 |
| 复审 | Codex + DeepSeek，其余 9 条锚点 | 7 条双过，2 条不过 |

“任一份不过即整批回退”的原规则对严格评审几乎不可满足（同一条锚点 Codex 前后两次判定也会不同，存在噪声）。**调整后的口径（已写入数据清单）**：偏好对只要求“选中的一侧被两位评审一致判更优”；锚点必须通过 Codex 全量严审且复审中无任何评审判不合格，否则剔除。据此剔除 6 条锚点，得到最终 26 行（16 对偏好 + 10 锚点）。Kimi 因 5 小时配额用尽未参与第 2 轮起的评审。训练在最终抽检完成前已开始，完成后按清单重启一次。所有评审均为模型评审，人工未核实。

已知的数据问题（评审指出、未全部解决）：过度保守（案件已记载碰撞却写“不能据此认定两车已碰撞”）、复合断言引用不完整、个别评价性字段降级为“不确定”。这些是 v3h 之后的改进方向。

## 7. 合并、量化与部署

1. **合并**：流式读取官方 BF16（18 个分片），对被适配的权重做 `W' = W + (α/r)·B·A`（fp32 计算、转回 bf16），未适配张量原样复制，约 12 分钟；可用 `--mtp_overlay` 覆盖 `mtp.*`。
2. **转 GGUF**：`convert_hf_to_gguf.py` 输出 bf16（54.6 GB），转换器会导出 MTP 层（`qwen35.nextn_predict_layers = 1`）；用 Q8_0 中转可把磁盘峰值从约 104 GB 降到约 80 GB。
3. **量化**：`llama-quantize` Q4_K_M → 16.8 GB（朴素量化，无 imatrix）。
4. **服务**：`harness/orin/serve_llama.sh`：`--reasoning-effort compact`、`--reasoning-budget 4000` + 提示语、每槽位 32768 上下文、`--spec-type draft-mtp --spec-draft-n-max 5`。

速度实测（Orin MAXN，同一份 10,550 token 的真实提示）：预填充约 230 token/s；解码无投机 7.49 token/s；官方 MTP 权重（草稿 3）13.74 token/s；重训 MTP 头（草稿 5）**16.30 token/s**（接受率 45.7%，草稿 3 为 57.6%）。

关于“能不能开关 LoRA”：llama.cpp 支持把 LoRA 转 GGUF 并在运行时叠加/调缩放，但实测（基座 IQ3_S + MTP）解码 14.7 → 11.2 token/s、接受率 72% → 49%、预填充 −10%，且 LoRA 无法合并进量化权重，故**交付合并版单个 GGUF**。

## 8. MTP 头自蒸馏

MTP 头是在原始基座上训练的，主模型被微调后接受率从 72% 掉到约 48%（v3f 上约 42%）。结构按 llama.cpp 与 vLLM 的实现核对：输入为主模型最后一层归一化后的隐藏状态 h 与下一个 token 嵌入，各过 RMSNorm、拼接后经 `fc`（10240→5120）、一个全注意力解码层、`mtp.norm` 与共享 lm_head；权重为官方 BF16 里 15 个 `mtp.` 张量（约 4.25 亿参数）。训练：冻结主模型（含 LoRA），缓存隐藏状态后在缓存上训 `mtp.*`；损失为主模型分布对 MTP 分布的 KL + 0.2×交叉熵，展开 3 步（权重 1.0/0.6/0.4）。离线一致率（留出集）：官方权重 73.8/59.2/49.5% → 训练 3 epoch 后 78.9/70.6/65.2%；真实接受率低于离线值，需在量化后实测。MTP 只影响速度，不影响贪心输出。**v3h 之后需在终版模型上重训**（待补）。

## 9. 局限与风险

- 数据全为合成；评分全为自动口径，未经人工核实；独立评审之间存在显著分歧与噪声（Codex 严、DeepSeek 松）。
- 与教师的差距（−1.4～−1.7 分）与硬门失败率（v3f 8/50 对教师 3/50）尚未达到既定通过线；v3h 的效果待评测。
- 后训练集规模很小（26 行），主要用于“线上协议适配 + 37 项解读”的校正，不是能力的大幅提升。
- 窗口：首版部署按每槽位 32768；工具回合与修订轮会超限，需系统层拆多次调用；训练窗口上限 32768，更长上下文是未来工作。
- 线上请求若带 `reasoning.effort=high`，Qwen3.8 模板会报错，服务端必须固定档位；线上 `report_harness` 的端点校验仅认固定域名，接入本地模型需系统层改动；`json_object` 与思考段的交互需用终版模型实测。
- 模型不得用于正式定责；输出需人工复核。

## 10. 路线图

1. v3h 后训练评测、量化回归、MTP 重训、交付。
2. 更长上下文数据（超过 28,000 的提示、多回合工具往返、修订轮），配合系统层“超限拆分”。
3. 视觉部分微调（让模型更好地从图片/关键帧产出 37 字段事故信息），并研究与报告 LoRA 的融合；融合需用 BF16 基座合并后重新量化与重训 MTP。
4. 修复数据中的“过度保守”和“复合断言引用不全”，扩大偏好对规模；评审口径引入人工抽样。
5. 把“窗口超限拆多次调用”做进系统，并按拆分后的输入形态补数据。
