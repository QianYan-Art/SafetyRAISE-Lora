# 扩展指南

这份仓库设计为持续更新。下面是最常见的几种扩展，以及每种的注意事项。接手请先读 [`handover.md`](handover.md)；命令里的路径与环境见 [`reproduction.md`](reproduction.md)。

## 1. 补更长上下文的数据

- **现状**：训练窗口按 28,000 起步（后训练集放宽到 32,768，即部署槽位上下文）；首提示中位 ≈16.8K，答案 ≤≈5K，思考预算历史数据按 4,000 采集、交付取 5,120。预算 5,120 时首提示 >≈22.6K 的案件、读片段后的第 2–3 回合、修订轮会超窗（终版总评测 11/34 调用被截断，见 `handover.md` 第 6 节和 `deployment.md` §4）。
- **做法**：
  1. 放宽采样门：`live_batch.py --stable-limit <N> --output-reserve <R>`（`N ≤ 训练窗口`，`R` 为给思考+答案留的余量）；要采多回合就去掉 `--first-call-only`，必要时用 `--reviewer minimax` 取真实审查反馈。
  2. `post_pipeline.py`/`build_post.py` 的 `--max-len` 同步放宽。`harness/sr_eval/live/window.py` 与 `rows.py` 里有硬上限常量（`HARD_WINDOW=32768`），超过需同时改。
  3. **先在 Orin 上测显存**：26.5K 序列峰值 43.3 GiB；**32K（31.9K）实测峰值 47.5 GiB**（约 +0.8 GiB / 1K token，外推与实测吻合；`--longest_first N` 让最长行第一个更新就暴露问题）。40K 以上外推约 52 GiB，统一内存只有 ~61 GiB（其中系统与页缓存还要占用），风险很高，必须单独实测，不要直接信外推。
  4. 同时放宽服务端 `-c`（每槽位上下文）与 MTP/KV 内存预算，并重做窗口截断核算（见 `deployment.md` §4）。
- **更好的办法**：若系统层改为“超限拆多次调用”，应按**拆分后**的输入形态补数据，而不是继续堆更长的单次上下文。

## 2. 补案件（多样性是瓶颈）

- v3b→v3c 的提升来自剂量与案件数一起上来；之后在同一批案件上加样本收益趋零（v3d/v3e）。新增训练样本应来自**没用过的案件**。
- 案件生成：`python -m sr_eval.cli gen-cases`（按 37 字段模板 + 指导意见提示词；事实量分稀疏/中等/丰富三档，稀疏档最贴近真实输入）。生成后更新 `harness/cases/<split>/`，并保证 train/dev/test 互不重叠。
- 每次新增后都要：确定性门 → 教师最小改动修订 → 独立评审 → 才进训练集；不要只看评审总分（评审与确定性覆盖率几乎不相关，且评审之间有分歧）。

## 3. 补偏好对 / 提高偏好对质量

- 优先“学生真实失败 → 修订通过”（`pair_revised`，同提示同思考前缀）。种子错误对（`seeded.py` 12 类）用来覆盖真实失败里少见的类别，但每个种子对必须**只引入一类错误**且被对应确定性检查判 fail（其余检查结果不变）。
- 已知缺陷待修：过度保守、复合断言引用不全、评价性字段降级为不确定（见数据卡 §4.4）。可以把这些做成新的确定性检查或种子错误类别。
- 评审口径：偏好对看“选中的一侧是否更优”；锚点要全量严审。评审用多个模型交叉（Codex 严、DeepSeek 松），并保留人工抽样的口子。

- **剂量经验（v3h 的教训）**：偏好间隔对“几处小编辑”的信号很弱（损失几乎不动）；26 行、13 次更新、lr 4e-5 基本不改变行为。要改变行为需要更大的剂量与更直接的监督（提高 `--sft_lambda`/锚点权重、lr 到 1e-4 量级、更多没用过的案件）；每次先用开发案首回合的确定性指标（`live_compare.py`）核对，不要只看训练损失。

## 4. 视觉部分微调与两份 LoRA 融合

- 本 LoRA 是纯文本（训练时视觉塔被丢弃，适配器中 visual 张量为 0）。
- 若要让模型更好地从图片/关键帧产出 37 字段事故信息，需要多模态训练栈（含视觉塔与投影），另训一份视觉 LoRA。
- **融合**两份 LoRA 产出新模型时：
  - 用官方 BF16 基座合并，而不是在量化文件上叠加（运行时叠加更慢且无法合并进量化权重）；
  - 两份 LoRA 都是基于同一基座的 `W += (α/r)·B·A`，线性叠加可以做，但互相干扰需要在报告任务与视觉任务两边都评测；
  - 融合后必须**重新量化 → 量化回归 → 重训 MTP 头**，MTP 头是针对具体主模型隐藏状态训练的。
- 部署上，视觉输入需要 `mmproj` GGUF（来自官方基座的视觉塔）。

## 5. 换基座 / 换量化

- 训练栈、冻结边界、`--lora_from`、MTP 头结构都按 Qwen3.8-27B 的层数与结构写死了（64 层 = 48 线性 + 16 全注意力），换基座要重核对这些。
- 量化回归：Q8_0 / Q6_K / imatrix-Q4_K_M / 朴素 Q4_K_M 在同批开发案上比硬门、评审分、思考长度和速度，再定精度。

## 6. 提交规范

- 数据：新增数据放 `datasets/<名称>/`，带 `manifest.json`（来源、数量、哈希、质量门、`human_verified`、`release_eligible`）；原样保存的发布包不要改动（哈希绑定）。
- 不要提交：权重、GGUF、原始采样轨迹/教师响应、外部调用账本与凭据、线上系统源码与部署配置、真实案件相关材料。
- 每次更新在 [`changelog.md`](changelog.md) 追加一条（日期、改了什么、关键数字、未验证项）。
